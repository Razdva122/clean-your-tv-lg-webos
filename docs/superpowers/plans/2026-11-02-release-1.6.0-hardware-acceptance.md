# Release 1.6.0 supervised hardware acceptance plan

**Goal:** Accept the selected candidate on identified test devices, including an original-signer Android upgrade without loss of existing data.
**Execution:** One observed action at a time in the current chat. The maintainer supplies physical observations; the agent prepares commands only after the device and operation are identified. This is a test protocol, not authorization for unattended device changes.
**References:** [Release flow](../../RELEASE-FLOW.md), [Android readiness](../../../android/STABLE-READINESS.md), [Root test plan](../../../root-edition/TESTING.md), [signed Root admission](../../development/SIGNED-ROOT-CANDIDATE-ACCEPTANCE.md), [candidate hashes](../../history/2026-11-02-release-1.6.0-artifacts.md).

## Stop rules

Stop the sequence on lost controls/audio/data, an unexpected version or signer, unknown state, a failed admission check or missing independent recovery. Preserve current journals and receipts. Do not uninstall Android, clear its data, reset the TV, delete recovery records, force a downgrade, re-sign the APK or patch supervisor trust. A stop starts diagnosis; it is not permission for a blind Restore/reinstall.

No installation or update may be active during a reboot, standby or power-removal test. Fault injection, process killing during TV writes, supervisor replacement and Homebrew failsafe tests require a separate bounded step with verified recovery and explicit owner agreement. Never interrupt an existing unresolved recovery merely to obtain a test case.

## Step 0 — Identify devices and scope

- [ ] Record whether the TV/phone are maintainer/project-owned test devices or another user's devices, and confirm the owner is present.
- [ ] Record TV model, firmware/webOS, Magic/IR remote, Root or No-root, current installed component versions and intended HD/FHD variant. Unknown values remain unknown until read safely.
- [ ] Record phone model, Android version, WebView version, installed CYTV version/code and installation source. Confirm ARM64 and supported OS/WebView before offering the APK.
- [ ] Ask whether either device has an unresolved operation or recovery. Record whether a computer with ADB and an existing trusted TV connection is available; do not discover or pair automatically.

**Exit:** Select one device/edition and actual upgrade baseline. An absent older Android installation cannot establish an in-place upgrade.

## Step 1 — Baseline and independent recovery

- [ ] With the current version, confirm Home, Back, arrows/OK, volume/mute and ordinary app launch. Record current sound output and startup behavior.
- [ ] Inventory existing phone profile aliases/count, selected edition/language, imported-key presence, existing TV trust/pairing and pending-receipt state privately. Compare actual state rather than printing keys or addresses. Passwords requested on demand are not evidence of lost stored credentials.
- [ ] Retain existing exact-version rollback packages and supported off-device recovery material privately with restrictive permissions. Android backup is disabled; do not promise a complete phone backup or use uninstall as recovery.
- [ ] For Root, inspect actual installed supervisor, recovery/rollback caches and unresolved journals using the supported read-only route. Verify independent recovery works before changing Home routing. A pinned System 1.1.2 device has no general migration path to 1.2.0; do not replace it to fit this plan.

**Exit:** Existing state is understood and a device-appropriate recovery route is available. A pre-existing failure is a baseline failure, not a candidate regression.

## Step 2 — Verify and install the Android update only

- [ ] Verify the retained candidate APK hash against the fixed input above and its protected-CI signer/provenance. When available, inspect the installed APK certificate and version/code with ADB/apksigner, retaining only redacted identity results.
- [ ] Close CYTV after confirming no TV operation is running. Update over the existing app with the original signed APK using Android's Update flow, or a device-specific `adb -s SERIAL install -r APK` command prepared after selecting the serial. Do not use downgrade flags, uninstall or clear-data.
- [ ] Require a successful package update and version 0.6.0/code 17. On a signature or version conflict, stop and retain the original installation.

**Expected:** Android accepts an in-place update; package ID and signing identity remain unchanged. No TV operation is started.

## Step 3 — Prove retained Android state

- [ ] Open the updated app; compare baseline profile aliases/count, edition/language, imported-key selection and existing trust. A profile visible in a list alone does not prove its key works.
- [ ] On a healthy idle TV, explicitly request a supported read-only status using an existing profile/key. Record whether authentication works without re-importing the key or recreating the profile. Record legitimate on-demand password requests separately.
- [ ] If an unfinished receipt existed before upgrade, verify it is still unresolved with the same operation identity/state, no automatic replay and no second install admitted. Do not clear it for testing. If none existed, mark receipt-retention NOT TESTED on this phone.
- [ ] Close/reopen, rotate, background/return, lock/unlock and force-stop/relaunch the idle Android app one at a time. Recheck selected profile, pending-state visibility and absence of automatic TV requests after each transition.

**Expected:** Existing data remains usable after update and process recreation; no automatic recovery or install.
**Coverage limit:** Exact pending-receipt retention can use a separate isolated original-signer instrumentation fixture if available. Test-signed/emulator or synthetic-file results must not be promoted to physical real-key/TV recovery. Do not plant synthetic receipts on a personal installation.

## Step 4 — Admit the exact TV packages

- [ ] Compare the selected installer's embedded payload hashes/versions with the frozen record and choose the detected compatible graphics variant. Record the user's explicit choice when selection needs confirmation.
- [ ] Root: obtain the protected Root-only QA signing artifact for **full build 41343868494:2**, using the existing workflow with tag `v1.6.0`, `publish=false`, `candidate_build_run=41343868494`. This is signing of the selected full build, not dispatch of a replacement preliminary build. Verify signing provenance, signature, envelope and all three exact package hashes. Keep signing-run identity with the full-build identity.
- [ ] Root: run existing read-only candidate admission with the owner present. Capture the actual current running UI profile privately for the supported install request. A refusal is BLOCKED; preserve installed trust/supervisor/cache state.
- [ ] No-root: use the final embedded Home/Helper packages through supported installer checks. Verify Developer Mode and existing connection without bypassing preflight or enabling Home implicitly.

**Exit:** The exact device-compatible route is admitted. Unsigned aggregate output is not a substitute for Root signed admission. A missing HD rollback blocks the corresponding legacy HD feed path. Ordinary OTA does not replace an independently pinned supervisor.

## Step 5 — Install/update and separate the outcomes

- [ ] Perform only the admitted edition's supported install/update with the owner present; record the selected versions and actual completion status.
- [ ] Verify package installation separately from app launch/startup, then verify the actual physical Home button from an ordinary application screen.
- [ ] If Home has not yet been physically tested, leave it skipped/unverified in the installer result. Record any initial error even if a workaround later succeeds.

**Expected:** Correct package versions, successful launch and observed physical routing are three separate results. A successful installer response alone does not pass Home.

## Step 6 — Controls and audio

- [ ] Test short Home from ordinary screens in two available apps. Test Back navigation, Back exit cancellation and confirmed exit. Record the visible destination and any LG flash.
- [ ] Test arrows/OK, held-arrow release, volume/mute and app launch; Magic pointer/wheel where present. Mark unavailable controls NOT TESTED; one remote does not establish IR/Magic compatibility.
- [ ] Play known content using the baseline output. Verify actual audible playback and volume/mute, not only UI indicators.

**Expected:** Intended Home routing, normal unrelated buttons and restored/retained sound. Root observations must establish that the No-root interception helper is stopped through the supported guarded route.

## Step 7 — Explicit Off and emergency release

- [ ] Use the edition's supported Off control; verify ordinary LG Home and sound, and that the UI status reflects Off. Explicitly re-enable only after recording that result.
- [ ] Exercise three completed Home presses within two seconds for the selected current Helper/Root emergency mechanism. Verify return to LG, working unrelated controls and no automatic re-enable. Record whether input is actually supported by this remote.
- [ ] Leave emergency Off latched through the next startup checks. Resume only by an explicit owner action after Off persistence is confirmed.

**Expected:** Emergency and explicit Off remain authoritative. Do not repeatedly activate a failing routing path.

## Step 8 — Standby and true cold boot, Off then On

- [ ] With Off latched and no operation running: standby/wake; verify LG routing, controls, sound and persistent Off.
- [ ] Still Off: perform an owner-controlled true AC-off cold boot only when the TV is idle, with no update/write or panel-maintenance cycle running. Record the power-removal interval and visible startup; verify Off, controls and sound again.
- [ ] Explicitly enable the intended Home behavior. Separately repeat standby/wake and true cold boot, recording initial foreground, short-Home routing, key release and sound after each. Do not hold navigation/Home while waking.

**Expected:** No unintended re-enable in Off; intended startup/routing in On; audio and controls survive both kinds of transition. The existing #171 wake report remains unresolved until matching evidence addresses it.

## Step 9 — UI and graphics changes

- [ ] Verify actual selected HD/FHD layout, focus/scrolling, dialogs and theme selection on the physical renderer. Record the viewport/variant; do not install an incompatible graphics variant merely to fill the matrix.
- [ ] Inspect Czech and SC/TC sample text where relevant, including new settings/status screens and missing-glyph/clipping behavior. Verify theme application and retained language/layout/order after relaunch.

**Expected:** Readable text, reachable actions and retained configuration. Untested languages/resolutions remain explicit gaps.

## Step 10 — Supported retained rollback and recovery

- [ ] After confirming all writes finished and a verified prior cache exists, use the supported retained rollback for the admitted edition. Verify actual prior versions/bytes, profile/order/language, physical Home/Back/emergency, audio and startup after the transition. Reinstallation of the candidate is a separate admitted transition, not assumed safe.
- [ ] Only on a prepared test device, agree a bounded interruption at a documented safe point, the expected durable receipt and supported recovery route before attempting an interruption. Do not cut TV power or kill a worker during unknown writes.
- [ ] After an authorized interruption, verify preserved first error/receipt, no automatic reinstall, clear status and separately confirmed supported recovery. Check versions, physical Home, audio and retained data after recovery. If no safe bounded scenario is available, record BLOCKED/NOT TESTED rather than inducing uncontrolled damage.

**Expected:** Exact retained rollback and truthful recovery behavior. Android package data retention is separate from TV-edition rollback; neither implies the other.

## Step 11 — Record acceptance and remaining gates

- [ ] Review all scenario observations and failures. Prepare a redacted record with known/unknown device fields and explicit unsupported/untested paths; retain private captures and raw diagnostics locally.
- [ ] Update candidate acceptance only for completed matching scenarios and bind its evidence to `41343868494:2`. Do not fill acceptance with this plan. A product fix requires a new full build and affected retests.
- [ ] Re-read related issues before updating statuses. Do not mark unresolved original reports fixed from one successful device or improved diagnostics.
- [ ] Keep PR #210 draft while a required scenario fails/is blocked. Publication, feed verification and release issue notices are later actions; this session does not merge main or publish a release.
