## Initial findings, investigation and resolutions

The first renderer script completed its full independent pass with 22/24 passes;
all 11 service cases also completed. Two renderer assertions needed investigation.
No product fix or replacement RC was started for either result.

1. **Grid-only focus assertion:** the script required focus under `#tiles`, but
   ordinary navigation also reaches dock/top zones. Source tracing and an actual
   twenty-step visible-focus trace showed exactly one visible focus at every
   step, including nine steps outside the grid. Correcting the QA predicate
   passed; no navigation implementation changed.
2. **Theme fallback after fast API-driven language reloads:** the script accepted
   document/tiles readiness without awaiting `HomeUIReady`/ThemeManager startup.
   Theme startup deliberately retains a boot marker until presentation and two
   animation frames finish; reloading an unfinished boot selects Classic recovery.
   The original cached theme was still present with its exact digest. It was
   restored through the supported installed-theme API, with the original wallpaper
   source restored and verified. The affected pass then awaited actual readiness
   and a clear boot marker before every next reload: all 13 locales retained the
   theme/digest, and the final raw language/theme/layout/trial preferences matched.
   This supports a harness-precondition diagnosis, not a candidate regression.
   Initial failed observations and private traces are retained rather than erased.

Root control was not manually enabled or emergency-reset to make an update pass.
The original worker handled suspension/restoration in both directions; observed
Root intent/guardian remain active after forward, rollback, forward and wake.
No installer receipts, SSH keys, pairing credentials, private pins, boot tokens,
rollback caches or recovery state were manually edited. UI-test cleanup used the
captured actual preference and supported theme/wallpaper selection APIs.
